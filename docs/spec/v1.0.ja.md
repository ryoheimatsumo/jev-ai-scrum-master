# Jev AI Scrum Master — 確定仕様 v1.0

- 確定日: 2026-09-22
- 仕様バージョン: 1.0
- 対象実装: 初回OSSリリース v0.1.0
- 開発名: Jev AI Scrum Master
- CLI名: `jev-sm`
- ライセンス方針: 本プロジェクトのコードはApache-2.0。依存コンポーネントは各自のライセンスに従う。
- 位置づけ: TypeSafe公式製品ではない独立したOSSプロジェクト。
- この文書は実装の基準であり、実装済み・公開済みを表すものではない。以下のMCPツール名、CLI名、設定形式は新規に実装するインターフェースである。

## 0. 最終決定

**一つの開発タスクを、準備・実装支援・受け入れ確認・振り返りまで支援する、既存コーディングエージェント向けのOSS。**

Codex / Claude Codeを置き換えない。会議を模倣するAIでも、新しいJiraでもない。実装AIの「実装しました」をそのまま完了にせず、合意した条件に対する検証結果を管理する。

ユーザー向けの基本単位は「開発タスク」とする。「マイクロスプリント」はUI、CLI、データモデルの用語として採用しない。一つのタスクには、必要に応じて画面・API・保存・テストの変更をまとめて含める。

成果指標は、誤った完了判定、人間の確認・手戻り、受け入れ可能な成果までの総負担。会議数、ストーリーポイント、生成コード量は主要指標にしない。

### 決定の優先順位

1. ユーザーが承認した目的・受け入れ基準・許可範囲。
2. プロジェクトの必須品質条件と権限制約。
3. 実際の検証結果と版の整合性。
4. レビュー担当LLMによる解釈。
5. Jevによる限定的な分類・確認。

下位の判断は上位の条件を取り消せない。特に、Jevの高いconfidenceは完了・権限付与・基準緩和の根拠にならない。

## 1. 対象ユーザーと利用環境

### 1.1 対象

- Codex / Claude Codeを利用する個人開発者、小規模開発チーム。
- AIへの実装依頼後に、仕様の抜け・未検証・再発を人間が確認している利用者。
- 自分が権限を持つローカルGitリポジトリ。

### 1.2 初回リリースの制約

- 1ワークスペースにつき同時実行中のタスクは1件。
- 実装担当は1セッション。検証レビューは別の読み取り専用セッションで順次実行する。
- 複数タスクの準備と保存は可能だが、自動の並列実装・競合解決は行わない。
- ホストはCodex CLIを参照実装とし、Claude CodeにもMCP・Skillとレビューアダプターを提供する。
- 対応OSはmacOS / Linux。Windowsネイティブは初回対象外。
- 対象アプリの言語は限定しない。ただし自動検証には、承認済みの実行コマンドと結果を解釈できるアダプターが必要。
- 初回の検証アダプターは、終了コード、JUnit XML、JSON Schemaで定義した独自JSONレポート。既存のテストツールを使用し、テストフレームワーク自体は作らない。
- モバイルは既存のテストコマンド・エミュレーター環境を利用可能。端末操作やエミュレーターの自動構築は含めない。

### 1.3 提供物

1. ローカルのCore / CLI / stdio MCPサーバー。
2. Codex用Skillと設定例。
3. Claude Code用Skill、設定例、任意の完了確認フック。
4. 受け入れ確認・振り返りのMarkdown出力。
5. 決定的な回帰テスト、比較評価用データ、評価実行スクリプト。

独立したWebアプリ、SaaSアカウント、クラウドDBは初回に作らない。

## 2. ユーザー体験

### 2.1 初回セットアップ

`jev-sm init`はリポジトリ、既存の仕様、テスト設定、ホスト機能を検査して設定案を表示する。ファイル変更は差分を提示して承認後に行う。既存のAGENTS.md、CLAUDE.md、Skill設定を上書きしない。

設定するもの:

- リポジトリルート、既定ホスト、レビューに使うホスト。
- プロジェクト共通の完成の定義(DoD)。
- 読み取ってよいファイル、送信しないファイル、検証時の除外出力パス。
- 承認済みチェックのコマンド・引数・作業ディレクトリ・実行権限・出力形式。
- Jev利用の明示同意とAPIキー参照先。
- 環境への変更を伴う操作と人間承認の条件。

外部送信を無効にした場合はJevを呼ばず、機能の縮退状態を表示する。他のLLMへの外部送信はホスト側の設定にも依存するため、完全ローカル推論とは表示しない。

### 2.2 通常の利用

ユーザーは利用中のホストで依頼する。

> 「スポット変更機能を、スクラムマスター付きで進めて」

ホストのSkillがCoreにタスクを登録し、既存仕様・コード・テストを確認して、計画を構造化する。Coreが不足項目とJevの補助判定を返す。

ユーザーには一枚のタスクカードを提示する:

- 目指す成果。
- 今回含む範囲 / 含まない範囲。
- 受け入れ基準と検証方法。
- 判断が必要な点。
- 実行するチェック、利用する外部モデル、重要な副作用。

計画を承認したら、承認された範囲内の実装・テスト・修正は毎回の承認なしで進める。ホスト固有の実行承認は別途尊重する。

完了時には、達成した基準、証拠、実行対象の版、残課題、振り返り候補を表示する。完了報告のために新たな会議やKPT入力を要求しない。

### 2.3 人間への確認

必須の確認は以下に限定する。

- 初回の計画・受け入れ基準・検証方法の承認。
- 未解決のプロダクト判断。
- 受け入れ基準の変更、必須チェックの緩和、重要な対象範囲の変更。
- 主観的・手動の受け入れ基準の確認。
- 新しい権限、未承認コマンド、新たな機密情報の外部送信。
- 自動修正上限後の再開、改善ルールの採用。

既存文書やコードで解決できる事項は先に調べる。人間への質問は決定に必要なものをまとめ、既回答の質問を再度出さない。

| ID | 必須機能 | 初回リリースの実装内容 |
|---|---|---|
| F01 | 計画・準備確認 | 要求、範囲、依存、検証可能性、未確定事項の整理 |
| F02 | 受け入れ基準 | 観測可能な条件と検証方法のひもづけ、版管理 |
| F03 | ストーリー分割 | 小さく検証可能な成果への分割提案と親子タスク管理 |
| F04 | 実装中の支援 | 失敗反復、環境ブロック、範囲逸脱、検証不足の指摘 |
| F05 | 受け入れ確認 | 管理されたチェック実行、証拠保存、基準別状態、完了条件 |
| F06 | 振り返り | 実行記録に基づく改善候補の生成、限定適用と採用管理 |
| F07 | 既存環境統合 | stdio MCP、Skill、CLI、ホスト別の任意フック |
| F08 | 再開・監査 | 状態永続化、証拠の版照合、承認履歴、実行再開 |

### 初回に含めないもの

Jira / Linear / Slackへの直接更新、PR作成・マージ・デプロイ、人の評価、会議運営、ストーリーポイント推定、並列エージェント指揮、汎用の前提依存グラフ、会話履歴の書き換え、モデルの再学習、承認なしの自己改変、完全な自律バックログ消化。

OpenSpecなどの既存Markdown仕様は読み取り入力として対応する。出典ファイルと内容ハッシュを記録し、外部仕様を勝手に編集・アーカイブしない。双方向同期とOpenSpec CLIの自動実行は初回対象外。

## 4. 役割分担

### 4.1 ホストLLM / 実装担当

要求の理解、参照情報の探索、計画案、AC案、ストーリー分割、コード実装、不具合修正、振り返り案を作る。Skillの指示に従ってMCPを呼ぶ。

MCPが利用中のチャットモデルを勝手に呼び出せるという前提は置かない。計画の文章生成はホスト側で行い、MCPには構造化した案を送る。

### 4.2 検証レビュー担当LLM

実装担当の会話を継続せず、別の新規セッションで、承認済みの条件、コード差分、検証用スナップショット、テスト結果だけを読む。

役割は、検証方法がACを実際に確認しているか、実装と条件に明白な不一致がないかを評価すること。コード・テスト・AC・Coreの状態を変更しない。

Codexは非対話実行と構造化出力、Claude Codeは非対話実行と構造化出力をアダプター経由で利用する。[S4][S5] 同一モデルでも別セッションは用意する。ただし別セッションだけで統計的独立性や正解を保証するとは表示しない。

ホスト機能や認証が利用不可の場合、必須レビューを省略せず`BLOCKED`にし、人間が同じ証拠に対してレビューを代行できる。

### 4.3 Jev

狭い範囲の意味判定・仕分けを担う。具体的な使い方は第10章。仕様作成、コード生成、総合的な正しさの証明、権限制御は担当しない。[S1]

### 4.4 Core / Runner

状態遷移、承認、バージョン、実行許可、予算・回数制限、テスト実行、証拠記録、完了条件を決定的なコードで管理する。

### 4.5 人間

製品上の判断、計画の承認、基準・権限の変更、手動基準の確認、改善ルールの採用を行う。

## 5. 計画・準備・分割

### 5.1 Task Contract

実装開始前に以下を契約として固定する。

| フィールド | 必須内容 |
|---|---|
| task_id / title / kind | 一意ID、名称、feature/bug/refactor/test/docs/spike |
| goal | 誰のどの問題を、どの成果で解決するか |
| in_scope / out_of_scope | 今回含めることと含めないこと |
| source_refs | 要求・仕様・コードへの出典と内容ハッシュ |
| acceptance_criteria | ID、前提、操作、期待結果、検証種別 |
| verification_plan | ACとcheck_idの対応、期待する証拠、手動基準 |
| dod_profile | プロジェクトの共通品質条件 |
| dependencies / blockers | 前提タスク、技術調査、環境・権限の不足 |
| approved_assumptions | 人間が承認した仮定とその適用範囲 |
| review_profile | light / standard / strict |
| allowed_actions | コマンド、範囲、ネットワーク等の許可 |
| budget_policy | 修正回数、反復、実行時間等の上限 |
| contract_version / contract_hash | 改訂番号とハッシュ |
| approval_ref | 承認者、日時、対象ハッシュへの参照 |

ACは原則としてすべて必須。任意の改善はACに混ぜず、`follow_ups`に置く。必須条件を満たさないまま「一部完了」を`DONE`にしない。

### 5.2 DoR — 着手してよい条件

必要なのは「不確実性がゼロ」ではなく、以下が着手に十分な状態であること。

- 成果と範囲が定義されている。
- 各ACに観測可能な結果と検証方法がある。
- 重大なプロダクト判断が未確定のままになっていない。
- 必要な依存関係・環境・権限が利用可能、または合意した調査タスクとして分離されている。
- 確認できない条件が隠されておらず、手動確認する場合は方法と担当が決まっている。
- DoD、実行するチェック、承認対象が定義されている。

欠損フィールドはCoreが指摘する。意味上の曖昧さはJevが候補を指摘し、LLMが解決する。Jevの指摘だけで修正ループを無限に回さない。

### 5.3 AC

条件ごとに`id`を与える。Given / When / Then形式を標準表示とし、UI評価などでは同じ情報を自然文で記載可能とする。

例:

- AC-01: 未予約スポットAがある旅程でBへ変更すると、対象箇所がBになる。
- AC-02: 同じ操作で、対象外のスポットのIDと開始時刻は変わらない。
- AC-03: 保存完了後に再取得すると、Bへの変更が残っている。
- AC-04: 変更APIが失敗した場合、保存済みの元の旅程が維持され、失敗が表示される。

これらは説明用の要件例であり、Tabi Craft AIの現在の確定仕様や動作結果を主張しない。

「使いやすい」「高速」といった基準は、そのまま機械判定しない。事前に測定条件を合意するか、手動確認基準にする。UIの画像評価をJevで代替しない。

### 5.4 分割

分割の単位はファイル数、会話ターン、行数ではなく、一つの検証可能な成果。単独で検証できるタスクは無理に分割しない。

機能変更は可能な範囲でユーザー体験を縦に通す。基盤作業や調査は、開発者向け成果や調査結論を独立した成果として扱う。`spike`は製品機能の完成を意味しない。

分割案はLLMが作り、Jevは一成果性・検証可能性・未解決依存の疑いを確認する。作成後は親の必須ACを子タスクに漏れなく対応付ける。子が複数でも同時実装はしない。子を完了しただけで、親の統合確認を省略しない。

### 5.5 計画変更

実装開始後にgoal、scope、AC、DoD、許可範囲、必須検証を変えると新しい契約版になる。旧版の承認と完了資格は失効し、`WAITING_USER`に遷移する。

単なる説明の追記や進捗記録は契約改訂にしない。本文変更を「意味は同じ」とJevだけで認定して承認を省略しない。初回は保守的に、契約項目の内容変更はすべて再承認とする。

## 6. 実装支援とレビュー強度

### 6.1 監視のタイミング

計画提出、検証の終了、障害報告、完了要求、再開時を主なイベントとする。毎トークン・毎キーストロークでは呼び出さない。

MCPで観測できるのは登録されたイベントと管理下の実行。未接続の端末操作やホストの全行動を監視できるとは表示しない。

### 6.2 支援内容

- 同じ失敗を繰り返す場合、環境確認・最小再現・別仮説の検証など、次の具体的な一手をLLMに作らせる。
- 仕様不足ならプロダクト判断へ戻す。認証やサービス停止なら環境ブロックとして扱う。
- 関係のない変更の疑いは根拠となる差分とともに通知する。必要なリファクタリングまで自動否定しない。
- 既に報告した同一問題は重複通知しない。

### 6.3 固定の3プロファイル

| Profile | 用途 | 追加レビュー |
|---|---|---|
| light | 明示的に承認された、動作変更のない限定的な文書・表記修正 | ACが決定的チェックで確認できる場合、LLMレビュー省略可 |
| standard | 既定。機能、バグ修正、通常の変更 | 別セッションでACとテストの対応・実装の整合性を確認 |
| strict | 認証・権限・課金・データ削除等、事前定義した重要領域 | 必須の否定系確認、別セッションレビュー、人間の最終受け入れ |

初回の自動調整はこの範囲に限る。既定はstandard。lightへの変更は計画承認時に人間が指定する。Jevはレビュー追加を提案できるが、自動的にlightへ下げたり、必須チェックを削除したりできない。

重要領域は設定したパスと操作分類で扱う。該当候補や領域不明はstrictの確認候補とする。途中でプロファイル変更が必要なら契約改訂として承認する。

### 6.4 ループ上限

- 最初の検証後、自動の修正サイクルは最大3回。初回を含めて最大4検証ラウンド。
- 同一の失敗指紋かつ関連する入力・コード・証拠に変化がない状態が3回続けば停止する。
- 失敗指紋はcheck_id、正規化したエラー、関連スナップショット情報から作る。単なる時間の経過は進捗とみなさない。
- 検証コマンドは既定600秒でタイムアウト。プロジェクトごとに承認して変更可能。
- Jev要求の既定タイムアウトは10秒、再試行は1回。
- 人間の応答待ち、権限不足、外部API停止はコード修正の回数を消費せず、待ち状態で保持する。無限の自動再試行はしない。
- 上限後は`BLOCKED`。現在の差分と証拠を保存し、再開には人間の明示承認が必要。

これらは管理下の実行に適用する。MCPのみを利用するホストの全トークン数・課金・作業時間まで停止保証しない。取得できない課金額は0ではなく`unknown`とする。

## 7. 検証と証拠

### 7.1 検証方法

1. 契約で指定したcheck_idを実行する。
2. Runnerがコマンド、実行環境、結果、テスト件数、レポートを保存する。
3. Coreが版の一致、必須チェック、失敗・skip・未実行を確認する。
4. Jevが証拠とACの対応に関する疑いを分類する。
5. 必要なレビュー担当が、ACを確認するassertionや実行結果が実在するか調べる。
6. 判定結果をACごとに保存する。

Jevの否定も肯定も、それだけで合否にしない。疑いには根拠への参照を要求し、必要なレビューで解決する。Jevを停止した場合も、必要な意味レビューは既定のレビュー経路か人間で実施する。

### 7.2 ACの状態

| status | 意味 |
|---|---|
| PASS | 指定の方法・同じ版・必要なレビューで条件を確認できた |
| FAIL | 観測結果が条件に反する |
| NOT_RUN | 必要な検証を実施していない |
| BLOCKED | 実行環境や権限等の理由で確認できない |
| NEEDS_REVIEW | 意味上の確認不足、主観判断、評価不一致 |
| STALE | 判定対象のコード・契約・検証条件が変わった |

`PASS`は定義されたチェックで確認できた意味であり、未知の不具合が存在しない証明ではない。

### 7.3 Evidence Record

必須項目:

- evidence_id、workspace_id、task_id、run_id、check_id、対応するAC ID。
- contract_version、contract_hash。
- snapshot_id、Git基準SHA、検証対象の内容ダイジェスト。
- 実行したコマンドの実体、引数、作業ディレクトリ、承認参照。
- 開始・終了日時、終了コード、タイムアウトや中断の有無。
- テスト総数、成功、失敗、skip。取得不可の場合はnullと理由。
- 生レポート、必要なログ、関連ファイル、証拠の内容ハッシュ。
- ランナー・アダプター版、OS、ランタイム、依存ロック、関連設定。
- 外部サービスを使った場合の対象環境、固定できない状態、検証時点。
- 信頼区分: managed_runner / approved_ci / human_attestation / agent_claim。

実装AIの自然文や`sm_report_progress`の申告は`agent_claim`であり、自動的に信頼済み証拠にしない。初回の自動採点はmanaged_runnerを標準とし、CI結果の読み込みは検証済みの取込形式だけに限る。取得元を検証できない外部レポートは参考扱い。

### 7.4 スナップショットと鮮度

HEAD SHAだけでは未コミット変更を捕捉できないため、trackedファイルと検証に関係するuntrackedファイルを含めた内容ダイジェストを使用する。

検証時は対象ファイルを隔離した実行用スナップショットへ固定する。テストのビルド出力・キャッシュは別の出力領域に置く。元の内容と、実行前後の検証入力ダイジェストを照合する。対象ソースやテストが実行中に変わったら結果を有効な証拠にしない。

成果物・依存ロック・設定・テストは検証入力。除外可能なのは承認済みの生成出力と明示した秘密ファイルのみ。検証に必要だがスナップショットに含められない入力は、別途フィンガープリントか人間確認が必要。秘密値そのものは保存しない。

初回はタスク単位の保守的な失効を採用する。対象入力が変わったら関連する最終検証セット全体をSTALEとし、依存グラフによる部分再検証は行わない。

環境・依存設定が変わった場合も再検証する。外部環境が固定できないチェックには有効期間と対象環境を契約で定義する。固定できない状態を完全再現可能とは表示しない。

### 7.5 「終了コード0」の扱い

終了コード0だけで任意のACを合格にしない。

- lint/buildなど、成功終了自体が合意した条件を確認するcheck_type=processは、その範囲で使用可。
- 行動テストでは、テストケース・assertion・実行件数とACの対応を確認する。
- zero tests、必須ケースのskip、レポート欠損、確認対象の取り違えはPASSにならない。
- mock成功しか確認していないのに、実保存・実APIの成功を確認したとは扱わない。
- ベースラインが失敗している場合は記録してBLOCKEDにする。既存失敗だからという理由だけで、必須チェックを自動免除しない。
- テストが不安定な場合、成功するまで実行して最後だけ保存しない。全試行を保持し、必要なレビューへ回す。

### 7.6 テスト変更

合意した検証方法を満たす新規テスト作成・必要な更新は実装範囲に含む。

既存必須テストの削除、skip化、必須assertionの除去、閾値緩和、検証対象縮小は人間承認が必要。Coreの差分検査とレビューで検出し、Jevのみで「問題なし」と解除しない。

## 8. 完了・承認・状態遷移

### 8.1 完了条件

以下をすべて満たした場合のみ`DONE`に遷移する。

1. 現行のTask Contractと計画承認が一致している。
2. 必須ACがすべてPASS。
3. 共通DoDの必須チェックがすべてPASS。
4. コード、検証入力、契約、環境条件に対して証拠が有効。
5. 必要な独立レビュー、手動確認、strictの最終受け入れが完了している。
6. 未解決の重大な指摘・権限問題・例外申請がない。
7. 条件判定と状態更新が同じ検証スナップショットに対して原子的に実行される。

`DONE`は本ツール内での検証済み完了。マージ、デプロイ、Jira Done、ユーザーの全体承認を自動で意味しない。

振り返り候補の生成失敗は完成した機能を未完了に戻さない。`retrospective_status=pending`として別管理する。

### 8.2 状態

| 状態 | 意味 |
|---|---|
| PLANNING | 準備と計画案の作成中 |
| READY | 現行計画の承認済み、未着手 |
| IN_PROGRESS | 承認範囲の実装中 |
| VERIFYING | 受け入れ確認中 |
| NEEDS_FIX | 検証で修正が必要 |
| WAITING_USER | 製品判断・承認・手動確認待ち |
| BLOCKED | 環境・上限・ホスト機能等で進行不可 |
| DONE | 第8.1節の条件を満たした |
| CANCELLED | 中止。未達条件は残したまま保存 |

主経路は`PLANNING → READY → IN_PROGRESS → VERIFYING → DONE`。

修正は`VERIFYING → NEEDS_FIX → IN_PROGRESS → VERIFYING`。

契約変更は新バージョンを作り`WAITING_USER`へ。承認後、着手済みならIN_PROGRESS、未着手ならREADYへ戻る。中断前状態を保存する。

DONE後に検証対象の内容が変わった場合、過去のDONE記録は履歴として残すが、現在の作業ツリーに対する完了資格は失効する。ユーザーが再開するとVERIFYINGまたはIN_PROGRESSへ戻し、新しい完了レコードを作る。過去の完了を削除・上書きしない。

### 8.3 不完全な成果と例外

未達条件を無視してDONEへ変更するoverride APIは作らない。

ユーザーが未達を受け入れて終了する場合はCANCELLEDまたは別の合意済み契約への再計画とし、元の未達を監査履歴と評価データに残す。評価時には、初期契約からの範囲縮小で成功率を水増ししない。

### 8.4 承認の出所

MCP入力に`approved=true`や`actor=human`を渡しても承認にならない。

承認はCore管理のローカル確認画面/CLI、または実装時に信頼経路を検証したホストの人間確認機構から記録する。対象のtask_id、contract_hash、内容、時刻を固定する。ホスト側の自然文「ユーザーが了承した」という申告は参考でしかない。

ローカル同一OS権限で動く悪意のあるプロセスまで完全隔離する製品ではない。承認記録やハッシュは、主として取り違え・古い結果・うっかりの迂回を防ぐ。敵対的なコードへの強制は、権限分離された環境やCIの保護と併用する。

## 9. 振り返りと改善

### 9.1 入力と出力

入力は契約変更、検証ラウンド、不合格、環境ブロック、再試行、人間の介入、最終結果。非公開の思考過程を取得・保存しない。

出力は、観測した事実、原因仮説、次回の改善案。仮説を事実として扱わない。人間への不要な通知を減らすため、1タスクから提案する改善候補は最大3件。

### 9.2 改善ルール

各ルールは以下を持つ。

- rule_id、version、名称。
- source_task_ids、根拠となるevidence_id。
- applicability: 対象のタスク種別、パス、操作、条件。
- proposed_action: 追加する確認・検証・計画上の注意。
- rationale_hypothesis: 改善できると考える理由。
- validation_result: 失敗再現ケースと無関係なケースでの評価。
- status: PROPOSED / APPROVED / REJECTED / RETIRED。
- 承認者、適用日時、ロールバック元。

初回は「計画時の注意と検証候補の追加」に限定する。権限拡大、セキュリティチェック削除、既存ACの緩和、Coreの自己改変、コードの自動パッチを学習ルールとして実行しない。

### 9.3 採用と適用

提案段階では次回の必須条件にしない。再現例と負例での確認内容を示し、人間の承認後に対象範囲を限定して利用する。確認例を作れない場合は「未検証の提案」に留める。

次のタスクの計画時に、まずパス・種別等で候補を絞り、Jevで意味的な適用候補を判定する。ルールはタスクカードに明示し、計画承認に含める。一度承認したルールでも、無関係な作業への強制はしない。

矛盾するルールを自動で混ぜない。旧版と新版が競合する場合は人間に整理を求める。ルールの取り消しは将来タスクに反映し、既に承認済みの契約は黙って変えない。

## 10. Jev判定仕様

JevのChoice、Score、Noulは型付き判断のプリミティブであり、文章生成や複雑な開発判断の代替ではない。[S1] 初回はChoiceとNoulを利用し、Scoreは必須としない。

| decision_id | 対象 | 出力/問いの例 | 使用方法 |
|---|---|---|---|
| readiness_gap | 計画の1項目 | NONE / REPO_LOOKUP / TECHNICAL_PROBE / PRODUCT_DECISION / UNKNOWN | 次に誰が何を確認するかの候補 |
| ac_observability | AC1件と確認方法 | 観測可能な期待結果が明記されているか | 不足候補をLLMへ戻す |
| slice_check | 分割案の1タスク | SINGLE_OUTCOME / MIXED_OUTCOMES / DEPENDENCY_UNCLEAR / UNKNOWN | 分割見直しの候補 |
| blocker_class | 1つの失敗と限定ログ | IMPLEMENTATION / ENVIRONMENT / REQUIREMENT / REPETITION / UNKNOWN | 調査先の選択補助 |
| evidence_relation | AC1件と証拠抜粋 | DIRECT_CANDIDATE / PARTIAL / UNRELATED / CONTRADICTORY / UNKNOWN | 必要な追加レビューの候補 |
| lesson_applicability | 承認済みルールと現在のタスク | この条件にルールが関係するか | 計画に提示する候補 |

### 入力

全会話や全リポジトリを送信せず、対象のAC、必要な前提、関連する差分/ログ、出典IDに限定する。前提が欠ける場合はUNKNOWNにし、データを切り詰めたことを記録する。

同じstateへの独立した問いは一要求にまとめる。先行回答に依存する問いはコードで次の要求へ分ける。[S1]

### 出力と閾値

型、選択肢、数値範囲、要求IDを検査する。未定義の選択肢や無効応答は判定失敗。

Choiceの初期confidence閾値は0.80。閾値未満、UNKNOWN、根拠欠損はレビュー候補へ回す。この値は初期設定であり、精度を保証する数値ではない。高confidenceでも自動合格、許可、基準緩和はしない。Noulの中間値は確定判断にせず、参照信号として扱う。

confidenceは回答分布の集中度を要約する指標であり、実業務の正答率と同一ではない。[S2] 全判定にmodel_id、質問版、state_hash、結果、分布、時間、利用量を記録して評価する。

Jevは説明文を生成しない。ユーザーへの説明は、判定カテゴリに対応する固定テンプレートと根拠への参照、必要時のLLM解釈で構成する。引用箇所が存在することはCoreで確認する。

### 障害時

タイムアウトや無効応答は`judgment_unavailable`。許可された既定レビュー担当へ回す。無断で別の外部プロバイダーにデータを送らない。必要なレビューが完了しない限り、対象条件をPASSにしない。

## 11. アーキテクチャと実装技術

### 11.1 構成

- Core: Python 3.12以上、Pydanticによるスキーマ検証、SQLiteの状態ストア。
- MCP: Python SDKを使ったstdioサーバー。初回は遠隔HTTPサーバーを公開しない。
- CLI: `jev-sm`。MCPと同じCoreを利用する。
- Jev: TypeSafe公式Python SDKをプロバイダーアダプターの裏に置く。[S1][S8]
- Runner: 許可済みの実行定義と隔離スナップショットでテストを動かす。
- Reviewer Adapter: Codex / Claude Codeの非対話実行を利用。スキーマ化した結果のみCoreへ取り込む。
- Artifacts: Markdownレポート、JSON実行結果。UIはホストの会話とCLI。

SDKとホストの具体的なバージョンはリリース時にロックし、対応機能の契約テストを通した組み合わせを公開する。未検証のバージョンでも動くと宣言しない。

### 11.2 ファイル配置

共有・レビュー可能な設定:

```text
<repo>/.jev-sm/
  config.yaml
  dod.yaml
  approved-rules/
  reports/                 # ユーザーが明示的に出力した要約のみ
```

ローカル実行状態:

```text
<user-state>/jev-sm/<workspace-id>/
  state.sqlite3
  artifacts/<run-id>/
  snapshots/<snapshot-id>/
  audit/
```

生ログ、実行DB、秘密値、承認用の内部情報はリポジトリにコミットしない。<user-state>はOS別のアプリケーション状態ディレクトリ。場所を診断コマンドで表示する。

### 11.3 永続化

Task、Contract、Approval、CheckDefinition、VerificationRun、Evidence、Assessment、Finding、ImprovementRule、Eventを管理する。Taskはworktree単位の排他制御を持つ。

状態変更にはexpected_revisionとidempotency_keyを使う。同じ要求を再送してもタスク、検証、完了レコードを重複生成しない。状態とイベントは同一トランザクションで更新する。

イベントは追記方式。ハッシュは破損や取り違えの検出用で、同一権限の敵対プロセスに対する暗号学的な保証としない。

## 12. MCP / CLIインターフェース

### 12.1 共通契約

- 入力・出力はJSON Schemaで検証する。
- 更新にはtask_id、expected_revision、idempotency_keyを持たせる。
- エラーはcode、message、retryable、next_actionを返す。
- MCPの`isError`とドメイン上の「未合格」は区別する。テスト不合格は正常に得られた業務結果。
- 長い検証はjob_idを返し、`sm_get_status`で結果を取得する。タスク実行はユーザーが起動したローカルプロセスの存続中だけに行い、ホスト停止後の継続を約束しない。
- LLMが任意コマンド文字列、承認者、証拠の信頼区分、最終PASSを自由に指定できない。

### 12.2 MCPツール

| Tool | 主入力 | 主出力 / 副作用 |
|---|---|---|
| sm_prepare_task | request, source_refs | task_id、収集すべき情報、計画スキーマ。PLANNING作成 |
| sm_submit_plan | task_id, plan, expected_revision | 正規化した契約候補、DoR不足、承認対象ハッシュ。既存契約変更もこの経路 |
| sm_start_task | task_id, expected_revision | 現行承認と依存を確認しIN_PROGRESSへ。無承認では開始不可 |
| sm_get_status | task_id, optional job_id | 状態、AC別判定、証拠参照、承認待ち、next_action |
| sm_report_progress | task_id, observation, refs | 非信頼の進捗記録、必要な調査候補。PASSは更新しない |
| sm_verify_acceptance | task_id, approved_check_ids | job_id。管理された検証を開始。任意shellは受け付けない |
| sm_request_completion | task_id, expected_revision | 完了条件を再計算してDONE、または不足条件。doneフラグ入力なし |
| sm_propose_improvement | task_id, proposal, evidence_refs | スキーマ検証済みのPROPOSEDルール。採用・必須化はしない |

計画案や改善案の自由文生成はSkillを通じてホストLLMが行う。Coreはテンプレート、根拠、統計を返して補助する。

### 12.3 CLI

```text
jev-sm init
jev-sm doctor
jev-sm serve
jev-sm status <task-id>
jev-sm approve plan <task-id> --version <n>
jev-sm approve criterion <task-id> --ac <id> --snapshot <id>
jev-sm verify <task-id>
jev-sm gate <task-id>
jev-sm review <task-id>
jev-sm resume <task-id>
jev-sm cancel <task-id> --reason <text>
jev-sm rule approve <rule-id>
jev-sm rule retire <rule-id>
jev-sm report <task-id>
```

これらは本仕様で実装するコマンド。現時点でインストール可能なパッケージと説明しない。

`gate`は当該タスク・版に対して条件を再計算する。終了コードは0=充足、2=未充足/確認待ち、3=証拠失効、4=ツール・実行エラー。`status`は参照のみ。

### 12.4 承認とレビューの経路

人間確認を必要とするCLIは、確認内容と対象ハッシュを表示し、エージェントからの入力だけで確認済みとしない。実装コマンド側に承認用権限を渡さない構成を推奨し、同一権限環境での限界を明記する。

Reviewerは読み取り専用スナップショットと必要なレポートだけを受け取る。Coreの書き込みツール、承認API、実装用編集ツールを付与しない。再帰的に本MCPを呼んでレビューを開始する設定は禁止する。

## 13. ホスト統合と強制範囲

### 13.1 Codex

stdio MCPを基本とし、Skillがタスクの準備・開始・完了確認を案内する。レビューは新規の非対話セッションを起動し、読み取り専用の権限と構造化出力を使用する。[S3][S4]

MCPだけでホストのすべての終了や編集を阻止するとはしない。本ツールのDONE状態はCoreが制御し、Git上のマージ禁止などが必要なら別のCI条件に接続する。

### 13.2 Claude Code

同じMCPとSkillを提供する。任意フックはTaskCompletedを利用できる場合に`gate`を呼ぶ。ただしTaskCompletedが発火する操作経路に限定され、あらゆる回答終了を捕捉するものではない。[S6]

Stopフックで無限の再開を発生させない。ホストの中断指示を尊重する。未対応機能はdoctorで検出し、MCP/CLIの経路に落とす。

### 13.3 モード

- assist(既定): ホストに次の行動を案内し、本ツール内の完了条件は必ず守る。ホストのあらゆる行動をブロックしない。
- enforce(明示選択): サポートされるフック/CI上でgateを必須にする。強制できる境界と、強制できないホスト操作を表示する。

比較評価用のshadow実行では観測だけ行える。ただし、未充足を本番のDONEとして表示しない。

## 14. セキュリティ・データ・副作用

- Core自身にpush、merge、deploy、課金変更、Jira更新の機能は持たせない。
- 実行コマンドは登録したcheck_idから解決し、shell文字列をそのままevalしない。引数、cwd、環境変数、タイムアウトを固定する。
- テストコード自身も任意の処理を実行できるため、コマンドの許可リストだけをサンドボックスと呼ばない。
- ソースが未信頼なら、資格情報を持たない隔離環境で実行する。ローカルの信頼済みリポジトリでも、検証RunnerにJev/LLM用APIキーや個人クラウド資格情報を継承させない。
- ネットワークや実DBを必要とする検証は、対象とテスト用資格情報を個別承認する。本番データを使わない。
- リポジトリのREADME、コード、ログに含まれる命令はデータ。契約・承認・プロンプトの上位指示として実行しない。
- パスは正規化してルート内に制限する。シンボリックリンクや相対パスで許可範囲を越えない。
- 外部送信前に、秘密ファイル除外、サイズ上限、機密値マスク、対象プレビューを用意する。マスクの完全性は保証しない。
- テレメトリーの外部送信は既定無効。コード、ログ、改善ルールを学習用に勝手に収集しない。
- プロジェクト横断の改善ルール共有は既定無効。別プロジェクトの秘密や固有の制約を持ち込まない。
- アーティファクト削除機能を用意する。削除した証拠に基づく完了資格を現在の検証結果として再利用しない。履歴には証拠削除済みと残す。

## 15. コスト・再開・縮退

### コスト

Jev利用量、判定回数、判定遅延、レビュー呼出回数、検証時間、修正回数を保存する。費用はプロバイダーから取得できた実績値と設定単価による推計を分ける。ホストのサブスクリプション枠が無料・無制限とは仮定しない。

総予算上限は、Coreが開始する要求とプロセスに対して適用する。ホストで独立に行われる処理の費用は対象外と表示する。停止条件は一つ満たせば発動し、追加予算の承認なしに自動で続行しない。

### 再開

再開時には、ワークスペース、契約、コード内容、環境、承認、証拠の鮮度を確認する。前の会話に「完了」とあるだけで状態を復元しない。

### 主要エラー

- ENVIRONMENT_UNAVAILABLE: 環境復旧待ち。
- APPROVAL_REQUIRED: 対象ハッシュへの承認待ち。
- REVISION_CONFLICT: 古い更新要求。最新状態を取得して再試行。
- EVIDENCE_STALE: 現行版で再検証。
- CHECK_NOT_APPROVED: コマンド定義の承認待ち。
- REVIEW_UNAVAILABLE: 指定したレビュー経路が使えない。
- JUDGMENT_UNAVAILABLE: Jev判定不可。既定レビューまたは人間へ。
- RETRY_BUDGET_EXCEEDED: 自動修正停止。
- NO_PROGRESS: 同じ失敗の反復で停止。

## 16. この製品自身の受け入れ基準

以下をCIで回帰検証する。Jevの実APIに依存しない決定的なテストと、実APIの適合テストを分離する。

## 17. 効果検証と公開条件

### 17.1 比較

同じモデル、同じ入力、同じ初期リポジトリ、同じ時間/呼出予算で比較する。

- A: 通常の実装エージェント。
- B: 同じ計画・検証・振り返りループ、Jevなし(ルール+同じレビュー担当)。
- C: BにJevの補助判定を加える。

初期予備評価は20タスク、各条件3試行を標準とする。タスクは動作変更、保存、異常系、権限、軽微な修正、曖昧要求を含める。統計的な一般化を保証する規模とは扱わない。

### 17.2 指標

- false_done: 完了要求/表示に対して、独立した評価で必須条件が未達だった割合。
- accepted_task_rate: 初期要求の必須条件を満たした割合。
- total_cost / wall_time / human_minutes: 正しく完了した成果までの総負担。
- unnecessary_interventions: 不要な停止・質問・レビュー。
- regressions: 既存の独立評価テストの悪化。
- repeat_failure_rate: 過去の改善対象と同じ失敗の再発。

初期契約と最終契約を併記し、途中で要求を削って成功率を上げない。価格不明は不明として集計から区別する。人間作業時間は手動記録または明示的に観測できた時間のみで、会話の間隔から推定しない。

改善ルールの検証は、学習元とは異なる保留タスクでも行う。Jevの閾値調整用データと最終評価データは分ける。

### 17.3 OSS β公開条件

P-01〜P-28、スキーマ/状態遷移テスト、対象ホストの実機連携スモークテスト、情報送信範囲の説明、既知制限の公開を必須にする。

A/B/Cの評価結果は成功例だけでなく全件を記録し、機密を除いた再現用データを公開する。予備評価が不足する場合は「機能β・品質改善未実証」と明示する。Jev導入で性能が改善するという主張は実測後に限る。

固定の「品質が何%上がる」「何倍速い」は仕様上の約束にしない。改善が見られなければ、Jevの判定対象を縮小して再評価する。

## 18. 実装順序

1. スキーマ、Core、承認、永続化、状態遷移、P-01〜P-08/P-21〜P-23。
2. スナップショットRunner、証拠、checkアダプター、完了gate。
3. Codex MCP/Skill/レビューアダプター、Claude Code互換と任意フック。
4. 計画・DoR・AC・分割のフローとJev判定アダプター。
5. 障害分類、有限の修正ループ、再開。
6. 振り返り、改善案の評価・承認・限定適用。
7. 評価ハーネスと公開用の一連のデモ。

これは開発順序であり、F01〜F09を初回の対象から外す意味ではない。第6段階まで含む一巡を初回の製品範囲とする。
